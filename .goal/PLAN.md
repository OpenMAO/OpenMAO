# OpenMAO: Signed Authority — identity + cryptographic signing plan

**One-line summary:** replace the shared token + typed-in actor name with real per-principal identity, and make the decisions that move authority (approvals, ratifications, org changes, chain heads) carry Ed25519 signatures — closing the gap the block/buzz audit identified as OpenMAO's largest evaluator-visible weakness, framed as ADR-0007 execution and ADR-0008 gate evidence.

**Risks worth stating up front:** (1) day-90 is 2026-09-09 and this is ~14.5–18 focused days (3–3.5 calendar weeks) that must not start before the external-human queue clears — and outreach time must be *reserved*, not assumed to fit in the gaps; (2) the boundary file was just rewritten by the console recovery and console Wave 2 is planned, so the extraction step (W4a) is not optional — this is the most likely source of a painful merge; (3) bootstrap writes a private key to the user's home directory, where a bug is a security incident rather than a test failure; (4) after this lands, signing is server-side, so a signature attests "the server, holding this principal's key, signed on presentation of this principal's token" — exactly as strong as the token, not stronger; browser-held keys are deferred and this must be written down, not glossed; (5) direct write access to the database file remains equivalent to root.

**What this plan explicitly does NOT do** (so scope cannot creep): no `AuthorityGrant`, quorum, or impact-gated approval authority (#94); no capability scoping (ADR-0011, ratified as "the most seductive over-build rabbit hole on the board"); no remote/TLS surface; no key rotation ceremony beyond revoke-and-attest-new; no corroboration *policy* change (the resolver is in scope, distinct-humans-vs-roles is #94); no canonical contract changes at all.

## Context

The 2026-07-24/25 block/buzz source audit (verified across four model families) settled two facts that drive this plan:

1. **The glass-house gap.** Buzz gives every human and agent a real cryptographic keypair; OpenMAO authenticates one shared workspace token and trusts a self-asserted `x-openmao-actor` header. Every separation-of-duties guard OpenMAO enforces (self-approval, proposer≠applier, corroboration distinctness) compares caller-supplied strings behind that one token — "modelled, not secured." This is OpenMAO's single largest evaluator-visible weakness, and the audit elevated it to the key input for the ADR-0008 day-90 adoption gate.
2. **The layer is empty but the clock is running.** Buzz shipped identity without authority (permission infra exists, unwired); OpenMAO shipped authority without identity. The audit's conversion test says: if OpenMAO opens its adapter lane without authenticated principals and a non-bypassable boundary, the shipped-COMPETITOR future wins by default. Building identity + signing IS the gate evidence.

## What buzz's permission system teaches us (the operator's question, answered)

**How theirs differs:** buzz's model is *identity-first, enforcement-last*. Access = membership (in the room → full member powers; no read-not-write, no risk tiers). Authority for agents = an owner-signed delegation credential (their NIP-OA "auth tag"): the operator's key signs a statement "this agent key acts under me, within these conditions." Approvals/gates exist as schema + endpoints + UI but are never enforced (runs marked Failed); delegation *conditions* are documented but never evaluated; credentials cannot be revoked. Ours is the inverse: *enforcement-first, identity-last* — deny-by-default gateway, durable approvals with at-most-once resume, self-approval guards, ceiling-bounded ratification — all real, all anonymous.

**What we take (concepts, not code — ADR-0003):**
1. **Real keys per principal** — every actor (operator, each agent, the service) holds its own keypair; "who did this" becomes verifiable, not typed-in.
2. **Owner-attested agent identity** — the operator's key signs each agent's key into existence (buzz's delegation idea), with two fixes buzz didn't ship: conditions that are actually **evaluated** on every authorization, and **revocation designed in from day one**.
3. **Signed decisions** — approval resolutions, autonomy ratifications, org-change applications carry the decider's signature; the audit trail becomes cryptographically attributable (what buzz's *design* promises and ours will actually *enforce*).
4. **Verification invariants** (from buzz's spec discipline, which was genuinely excellent): verify exact bytes (never canonicalize-then-verify); domain-separation tag per signed object type; resolve identity from OUR stored mapping, never from the presented credential (their owner-ban-cascade bug was fail-open on exactly this); fail closed on missing/invalid signatures.
5. **Published negative test vectors** for the signing layer (what a verifier MUST reject), using the envelope format specified in experiment E3.

**Traps we avoid (their mistakes):** private keys handed to the LLM process as env vars (ours go behind the existing credential-broker pattern — agents hold handles, never keys); unrevocable credentials; conditions-as-decoration; tamper-evident marketed as tamper-resistant; a 14-document protocol surface.

## Design requirements (settled — distilled from the audit, source-verified)

**Purpose of signing, precisely:** make the principal identifier authentic at the point where authority changes. Not payload protection (the store owns payloads), not federation, not a wire protocol. The authorship/authorization model already exists in the contracts (`BoundedWorkEnvelope.worker_id` + `issued_by`) — what's missing is the attestation; and the decisive gap is that every authorization's *lookup key* is caller-asserted behind one shared token (`ts/src/api/server.ts` requestContext; `ts/src/capabilities/registry.ts` actor-from-body).

**SA-0 (blocking prerequisite):** signing must not build on the current canonicalizer — the non-JSON rejection fix (the serialization polish, already built/measured, +49/−10) must land first; a signature over a non-injective preimage attests less than it appears to. Note: main already carries #129's guard; the polish adds the typed error + regression tests.

**What gets signed (value order):** SA-1 autonomy ratifications (the only irreversible-upward authority move; today proposer≠ratifier is a normalized-string compare) → SA-2 approval resolutions (signature is the version of the overturned `resolved_by` idea that actually works; unsigned resolution on a signature-required class must not resolve) → SA-3 principal registration (operator key attests each agent/worker key — buzz's owner-attestation concept with the two repairs: conditions stored as typed predicates and **evaluated at every seam**, revocation designed in from day one) → SA-4 org-change apply/revert (bounded value: one real applier today) → SA-5 signed event-chain checkpoints (closes `verifyChain`'s own documented truncation gap; ship with the honest tamper-evident-not-resistant caveat).

**Key design:** Ed25519 via `node:crypto` — zero new dependencies (buzz's secp256k1/Schnorr was Nostr conformance, not a security judgment). One key per principal (operator / each agent-worker / substrate service key for checkpoints only), no shared keys. Key records are first-class substrate rows (key id, principal id + actor_type, pubkey, algorithm, generation, validity window, status active|rotating|revoked, enrolment attestation ref) — **the verified key id, never a body field, becomes the lookup key for decisions**. Rotation = state transition preserving audit lineage; one operator command revokes all authority for a principal, one for the workspace.

**Verification invariants (each becomes a test):** V-1 verify exact stored bytes, never canonicalize-then-verify; V-2 versioned domain-separation tag per signed object type, preimage binds object id + workspace id (+sequence); V-3 resolve identity/standing from the substrate's stored mapping, never from the presented credential (buzz's ban-cascade was fail-open on exactly this), credentials establish records once and never decide; V-4 fail closed on missing/invalid/unknown/revoked/unevaluable — a check that cannot refuse is not a check; V-5 self-approval/self-ratification/self-attestation guards re-expressed over attested key ids, never satisfiable by null; V-6 signature validity clock-independent, authority freshness substrate-timed; V-7 one table-driven verifier, no per-object hand rules; V-8 verifier decisions (accept/refuse + reason + key id) land on the event record; keys and signatures never in logs.

**Custody:** extend the existing credential-broker shape into a **signer broker** — `sign(key_handle, domain_tag, bytes) → signature`; no API ever returns a private key. Operator key in the OS keychain; substrate/service keys in encrypted files (0600+KDF) for headless; env vars for test keys only. **No principal private key ever enters an agent/LLM process environment** (buzz's core custody mistake): spawned runtimes get constructed—not inherited—environments, with a test asserting no key-shaped variable reaches a child. State the residual honestly in LIMITATIONS: without a runtime sandbox, the boundary holds only while the signer runs where agents can't inspect.

**Anti-lessons bound into the design (do-not rules):** no new protocol surface (one preimage builder, one verifier, one tag table, one key table, one revocation table — no event kinds, no wire format, no spec documents); no per-type gating rules; no unrevocable credential (revocation ships in the same change as registration); no conditions-as-decoration; no tamper-resistance claims for tamper-evidence (scope claims to the checkpointed range); no advisory signatures (warn-then-succeed is forbidden); no membership-as-authorization tier beside the capability model; no assumption documented without its discharging mechanism + test in the same change.

**Test vectors:** extend the E3 envelope (`schema_ref` + `schema_sha256`, per-vector `target_def`/`vector`/`must_fail_because`) with a `class: "verify"` vector family — ~15 named negative vectors (wrong domain tag, cross-type replay, re-serialized bytes, non-JSON payload, unknown/revoked key, expired window per substrate time, unevaluable condition, self-attestation, missing signature, infra-failure fail-closed, non-canonical encodings, valid-credential-on-invalid-object) plus one positive vector published **with intermediates** (canonical bytes, digest, signature) so a second implementation can localize disagreements. Vectors are pinned to the build — a runnerless vector set is decoration.

**Explicit non-goals** (so scope cannot creep): no Nostr/relay/event kinds; no ECDH memory encryption; no memory version-lineage chain; no presence bytes; no `resolved_by` column; no external witness service.

**Two flags:** the A2 buzz-trust report never existed (its scope was re-verified via B1/O3 — provenance is sound but note it); and the signing branch must be cut from reconciled `origin/main` (which has #129) — this session's exploration worktree predates it.

## Implementation architecture

**Anchor rule:** all references below are to symbols, not line numbers — `origin/main`'s PR #130 rewrote `server.ts` (2119 → 2563 lines) and every boundary line number moved.

### ⚠️ The constraint that reshapes everything (found in design review, verified by execution)

**Any additive field on `EventSchema`, `EventPayloadSchema`, or `ExternalActorRefSchema` silently invalidates every already-chained event — and no test in the repo would catch it.** `verifyChain` re-parses each stored row through `EventSchema.parse` and re-derives the digest; zod materializes `.default()` keys on re-parse, so `{"a":"x"}` becomes `{"a":"x","sig":null}` and the hash no longer matches. Every test builds a fresh in-memory database, so such a change passes `make check` green while breaking `make verify-chain` on the operator's real database and every adopter's. The repo already reasoned to the same rule from the other side: its v7 migration comment says rewriting a chained row "would (correctly) read as tampering."

**Reconciled by execution (2026-07-26), because the two design passes disagreed.** The Claude architect said "add no contract fields"; GPT-5.6 proposed exactly the field the architect forbade (`principal_id` on the actor reference) plus authority-snapshot fields on the domain contracts. A probe against the repo's own zod settles it precisely:

| Change | Result |
| --- | --- |
| `principal_id` on the actor reference | **CHAIN BREAKS** for every stored event that carries an `actor_ref` (hash `fb3ecf…` → `089bfa…`) — the architect is right, GPT is wrong |
| events with no `actor_ref` | unaffected |
| authority fields on domain contracts (`ApprovalRequest` etc.) | **chain-safe** — `payload.data` is an opaque `z.record` and is never re-parsed through nested schemas, so GPT's blanket claim of danger here is over-stated |

So the *conclusion* is the architect's but the *reason* is narrower: the actor-reference change is a verified hazard and is forbidden; domain-contract fields are chain-safe but still engage the ADR-0002/0016 freeze and the pinned fixture, and none of them earn their keep this branch (see `resolved_by` below). Net posture: **zero canonical contract changes**, with the durability test as the guardrail rather than a rule taken on faith.

Three consequences, all of which **shrink** this branch:

1. **Signatures live in a sibling table** — never an `Event` column (a signature inside its own digest is circular), never `EventPayload.data` (that would break the replay contract). Note `EventPayload.data` is an opaque `z.record` and therefore hash-safe for *decision metadata*, which is where the verifier's decision goes.
2. **No `ExternalActorRef.principal_id` in this branch** (my earlier draft had it — it breaks the chain). Provenance→principal resolution goes through a lookup helper against the `principals` table. The typed migration of `requested_by`/`ratified_by`/`applied_by` belongs to issue #93.
3. **This branch adds ZERO canonical contract types or fields.** `schemas/canonical/v0.schema.json` is not regenerated, the fixture (repo-root `tests/fixtures/canonical_v0.json`) is untouched, `contracts.test.ts` is untouched, and the ADR-0002/0016 contract freeze is never engaged. **`resolved_by` is also dropped** — the approver is already recorded verifiably in two places written in the same transaction (the signature row's `signer_principal_id`, and the `approval.approved` event's `actor`, which is now trustworthy *because* it is bound). A third denormalized copy would engage the freeze to record data already recorded.

**Adopted from GPT that the architect missed:** keep chain checkpoints strictly separate from the existing run-resumption `Checkpoint` type (a real name collision — that type is run/node/state-specific); add a `signature_verifications` table persisting *rejected* attempts with bounded reason codes (this is the "verifier decisions are recorded" invariant made concrete); `ts/src/sdk/external-worker-client.ts` hardcodes the worker token and must be touched; unambiguous framing of the signed input (satisfied by the adopted JWS construction — superseding the bespoke length-prefix idea); registration conditions as a closed enum of *evaluated* predicates (`workspace_exists`, `subject_exists`, `attestor_is_active_operator`, `public_key_is_ed25519`, `fingerprint_is_unique`) each storing `{predicate, result, observed}`; and **legacy rows with no resolvable key fail closed — there is no null bypass**.

**GPT's sharpest self-critique, accepted as a named limitation rather than solved:** server-side signing proves *the server process possessed this principal's key on presentation of this principal's token* — not that a distinct human touched a hardware-backed key. Both designs share this. It is acceptable for this branch because ADR-0008's evidence clause asks for a hash-chain-verifiable slice or chain-head attestations — **integrity, not individual non-repudiation**. Non-repudiation needs browser- or device-held keys, which is a second protocol surface and ships with remote access. LIMITATIONS must say this in exactly these terms.

### The central split: token authenticates, key attests

Authentication and attestation are separated deliberately. A **credential token** proves *who is calling* on each request (reusing the proven worker path); an **Ed25519 key** signs *decisions that move authority*. Signing every HTTP request would be heavy for the console and buys nothing the token doesn't; signing decisions is where the guarantee is needed. This keeps the surface small — one new auth branch, one signer, one verifier.

### Data model — six new tables, explicit columns

`principals` (id, workspace, kind human|agent|worker|system, display_name unique per workspace, status, **`dev_bootstrap` flag**, created_at) · `principal_keys` (public_key unique, algorithm, status active|revoked, valid_from) · `principal_credentials` (the `worker_credentials` copy for humans: token_hash unique, hash-only) · `principal_key_attestations` (subject_key, attester_key, **`conditions_json` as evaluated typed predicates**, signature) · `principal_key_revocations` (unique per key, reason_code, signed) · `governance_signatures` (object_type, object_id, signer_key_id, signer_principal_id, body_digest, signature, domain_tag; **UNIQUE (workspace, object_type, object_id, signer_key_id)**) · `chain_checkpoints` (head_seq unique per workspace, head_hash, prev_checkpoint_id, signature, + append-only triggers).

Explicit SQL columns rather than `payload_json`, deliberately: principals and keys are read on every request (one indexed lookup), and explicit columns keep them out of the canonical schema bundle. The `governance_signatures` unique index is the at-most-once analogue of the approval CAS — replaying the same signature is a no-op, while a *second* signer on the same object appends a row, which gives quorum (#94) for free without designing it now.

### Signing mechanics — and how replay stays intact

**DECIDED 2026-07-26 after two standards reviews and a byte-level probe: use the RFC 7515 detached-JWS signing input, implemented over `node:crypto`, with no new dependency.**

Signing input is exactly the JWS construction: `BASE64URL(protected_header) || "." || BASE64URL(payload)`. Protected header is minimal and vanilla — `{"alg":"EdDSA","kid":"<key id>","typ":"application/openmao-<object_type>-v1+json"}` — so **domain separation rides the registered `typ` parameter** rather than a bespoke tag (and is repeated inside the payload, which is also signed). Payload is the existing canonical `dumpJson` output of the explicitly-enumerated decision body. Stored per signature: the protected-header segment, the exact payload bytes, and the signature. **Body builders still enumerate fields explicitly, never `dumpJson(entire row)`**, and the verifier re-reads the stored row — so it verifies against stored state, never client-presented bytes, and a future field becomes a new `typ` version while old signatures keep verifying.

**How three opinions reconciled.** K3 said bespoke, with a "wrap it in JWS later, no re-signing" hedge. GPT's deep review said the hedge is broken and ranked **DSSE** first (then JWS, then bespoke third). A byte-level probe settled the mechanics: a signature over payload bytes `P` does **not** verify against the JWS signing input `H.B64(P)` — Ed25519 binds the exact message, and the `b64:false` variant differs too. So K3's hedge is dead, and **the signed-input format is a genuine one-way door**: keys rotate, and an append-only log cannot be re-signed. That is GPT's decisive point and it stands.

Both reviewers then made the *same category of error* about cost. K3 assumed a standard could be retrofitted; GPT assumed JWS implies the `jose` dependency and therefore ranked DSSE first largely on "no dependency." The probe falsified that premise: a **fully compliant detached JWS was assembled and verified using only `node:crypto` and `Buffer`'s built-in base64url** — no dependency, about thirty lines. With the dependency cost equalized, JWS wins on GPT's own stated criteria: it is an IETF standard (RFC 7515) rather than a published-but-not-standards-body spec, and JOSE verifiers are ubiquitous in exactly the compliance and audit contexts that would ever check these signatures, whereas DSSE tooling is concentrated in software-supply-chain use. `jose` may be added later purely as a convenience, or never; either way no history is re-signed, because the bytes were standard from the first signature.

**Adopted from GPT regardless of envelope choice** (all zero-dependency, all orthogonal):
- **Public keys represented as RFC 8037 OKP JWKs** (`kty:"OKP"`, `crv:"Ed25519"`, `x`), with the **RFC 7638 thumbprint as `kid`** — stable under metadata change, computed from required members only. The private `d` member never enters the registry or any export. A JWK Set is a useful export; it is *not* the authority, and omitting a key from today's JWKS must never destroy the public key needed to verify yesterday's decision.
- **A distinct media type per semantic class** as the `typ` value (governance decision, principal enrolment, revocation, chain-head attestation) — never generic `application/json`. Once emitted these are protocol constants.
- **`kid` is an unauthenticated selection hint.** Pin Ed25519 in code; use `kid` only to select candidate keys; verify; *then* require the signed principal and role to match the registry.
- **Quorum counts unique authorized principals, not signature rows or key ids** — two keys held by one principal must never satisfy a two-person rule.
- **Migration does not manufacture history.** Existing decisions are explicitly `legacy_unsigned`; the owner signs a one-time **import attestation** over the schema version, workspace identity, and current chain head. That honestly proves "the new trust root accepted this imported state at time T" — not that historical actors signed anything.
- **`dumpJson` must be documented as a protocol, not a helper.** GPT caught that it sorts keys with `localeCompare`, which is *not* RFC 8785 JCS (that requires locale-independent UTF-16 code-unit ordering). It is very likely deterministic for the repo's ASCII field names on a pinned Node, but it must not be described as portable canonicalization: version it, specify the supported JSON subset and ordering, and ship golden vectors (non-ASCII keys, surrogate pairs, control characters, `-0`, exponent forms, rejected values). Because verification runs over *stored* bytes, portability matters only for a verifier re-deriving a payload from a domain object — but that is exactly the external-auditor case.
- **Future remote request signing uses RFC 9421 HTTP Message Signatures**, never the governance envelope repurposed as an ad-hoc request signer. Goes in the remote-access plan.

This settles interop honestly rather than speculatively: any JOSE-capable verifier — an auditor, an adopter's compliance tooling, another deployment — can check these signatures without OpenMAO publishing a spec for anyone to implement.

Four rules keep the replay contract intact:

1. **Signature bytes never enter an event payload** — they live in `governance_signatures`; the event payload carries only a deterministic signature-row *reference* plus the verifier's decision, inside the opaque, hash-safe `payload.data`. **Corrected justification:** an earlier draft claimed this is *what preserves* the replay test. It isn't — that test passes because the second `approve()` hits the already-approved early return and never appends a second event. The real reason the sibling table matters is sharper: the approval event embeds the **entire approval object** (`data: { approval_request: approval }`), so signature fields added to `ApprovalRequestSchema` would land inside the event payload after all, exactly what must not happen. Ed25519 determinism also only helps for the *same* key — a different principal or a rotated key produces different bytes.
2. **Deterministic Ed25519 is load-bearing, not aesthetic** — re-signing identical bytes yields identical bytes, so the unique index makes replay a no-op. A randomized scheme (ECDSA) would break replay outright. This is a second, independent reason Nostr's secp256k1-Schnorr choice doesn't transfer.
3. **Every timestamp in a signed body comes from the stored row, never `utcNow()` at sign time.** Get this wrong and a replayed approve produces different bytes, the unique index rejects it, and `governance.test.ts:286` fails. **This is the single most likely implementation bug in the branch** — call it out in the executor's brief.
4. **The already-approved early return stays exactly where it is**, before the self-approval check; signing is inserted after it, inside the same transaction as `resolve()` and the event append.

Verification never throws on a bad signature (a thrown verifier becomes a 500 and leaks timing) and fails closed in order: signature row exists → key resolves → attestation exists and unrevoked → conditions evaluate → principal agrees with the key mapping → Ed25519 verify over the **stored exact bytes**. Conditions are a closed union (`not_after`, `workspace`, `object_types`), not a DSL; an unknown kind fails closed.

**Superseded — recorded so the reasoning isn't relitigated.** K3 proposed a hedge: stay bespoke but put the domain tag, version, algorithm and key id inside the signed bytes, so a JWS wrapper could be added later without re-signing. **A byte-level probe falsified it** — JWS signs `BASE64URL(header) || "." || BASE64URL(payload)`, which is not the payload, so no historical bespoke signature can ever become a valid JWS signature. There is no cost-free later migration. That is exactly why the JWS signing input is adopted now (above) rather than hedged toward.

**Two properties the standards review flagged as least covered by this plan** — both must be explicit in the executor's brief: (6) **key lifecycle evaluated as of signing time**, not verification time (see the revocation rule below); and (7) **replay binding to an anchored event** — a signature must be bound to the specific event/sequence it authorized, so it cannot be lifted onto a later state transition of the same object.

**Four rules the review corrected, each load-bearing:**

- **Store the exact signed bytes.** `verifyChain` today parses a row and re-serializes it, which is *semantic* canonical verification, not exact-byte. And `dumpJson` sorts keys with `localeCompare`, which is locale-dependent and not a specified cross-language ordering. So the signature row must persist the literal `signed_bytes` blob; rebuilding them by re-running `dumpJson` would accept a reserialized record and defeat the very negative vector meant to catch it.
- **Separation of duties compares stable principal ids, never key ids.** Otherwise rotating a key lets one human become a "different person" and self-approve. Resolve verified key → stable principal first, then compare requester/proposer against resolver/ratifier/applier on principal ids. (Earlier drafts of this plan alternated between the two — the key-id version is wrong.)
- **Revocation must not retroactively invalidate history.** Verification returns two distinct answers: *cryptographic validity* and *authority-at-decision-time*, computed from `valid_from`, `revoked_at`, the decision timestamp, key generation, and a compromise flag. Revoking a key stops new authority; it must not turn every past signature into a failure.
- **The signed body binds intent, not post-hoc facts.** The envelope carries operation, object id, **expected current state/version**, signer principal, key generation, and decision time — and for apply/revert the authorization intent the human actually saw, not the mutation's after-state.

### Bootstrap and dev UX — the linchpin

**Every demo path runs through `cli.ts`** (`make demo`, `demo-approve`, `demo-deny`, `verify-chain` are all cli.ts entry points), and those demos are the gate-evidence path. So closing the CLI cannot cost the one-command experience:

1. **Configured path:** an existing key (env or `~/.openmao/keys/operator.pem`) is used. Production.
2. **Dev-bootstrap path:** otherwise generate Ed25519 via `node:crypto`, write PKCS8 at mode `0600` (refuse to overwrite; refuse entirely under `NODE_ENV=production` or when non-loopback is enabled), insert the principal + key, mint a token, and emit a `principal.bootstrapped` event recording the mode. Print id, token once, key path — the same shape as today's token print.
3. **The honesty valve:** a dev-bootstrap key's signatures verify but return `trust: "development_bootstrap"`. A dev signature never claims production trust, and the distinction lives in the audit trail rather than a README caveat. This is what lets `make demo` stay one command without lying.
4. **The demo exercises the real mechanism:** the demo's coordinator becomes an `agent` principal whose key is **attested by the bootstrap operator key** — so "operator attests agent keys" is exercised on every `make demo`, the strongest possible test.
5. **Token custody must be designed, not assumed.** Minting a credential while persisting only its hash leaves the *next* CLI invocation unable to authenticate. The bootstrap writes the plaintext token to a local profile file (`0600`, alongside the key, never in the database) — without this the one-command demo silently breaks on the second command.
6. **The demo needs no invented "reviewer."** It already has two semantic actors: the coordinator requests the approval and the operator approves it. The work is to *principalize the existing two*, not add a third. `demo-deny` **cannot remain unchanged** — it currently rejects with a nullable actor, which is exactly the null path being deleted. And `verify-chain` must never auto-provision or mutate a database just because it runs through the CLI: read-only commands stay read-only.
7. Explicit path: `make keys` / `principals init` / `principals mint-token` / `principals attest` / `principals revoke-key`.
8. **Custody is a matrix, not a fallback.** Spell out and test each: macOS keychain; Linux interactive; headless service (unattended KDF needs a passphrase source — storing it beside the ciphertext is cosmetic); CI static signer; and recovery. "Encrypted-file fallback" without an unlock design is a hole.
9. Acceptance is a literal test, not a claim: fresh tmpdir + `demo` → exit 0 with **no prompt**, second command authenticates from the profile, bootstrap event present, key file mode `0600`, key material absent from stdout and from every event.
10. **Bootstrap is an explicit root-of-trust transition, not an ordinary registration.** The first operator key cannot be owner-attested without self-attestation, so it needs a named one-time ceremony: valid only on an empty registry, recording evaluated predicates (`registry_empty`, `private_key_mode_0600`, database ownership), with the public-key fingerprint recorded **outside** the database so that replacing the root key and its enrolment records is not indistinguishable from a legitimate first run.
