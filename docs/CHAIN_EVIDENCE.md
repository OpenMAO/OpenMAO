# Chain Evidence: Exporting and Independently Verifying the Event Log

OpenMAO's event log is append-only and hash-chained, and an operator can pin its head with a
signed chain-head attestation (`openmao attest`). This document describes how to export that
evidence as a single JSON bundle and how a third party verifies it **without trusting the
database it came from** — the property the attestation mechanism exists to provide
([ADR-0020](adr/ADR-0020-signed-authority.md)).

A committed sample, produced from a fresh `make demo && make demo-approve` database, lives at
[examples/chain-evidence.sample.json](examples/chain-evidence.sample.json). Its signatures
carry `development_bootstrap` trust: the demo key is generated by the local bootstrap ceremony,
so the sample demonstrates the verification mechanics, not production authorship.

## Producing a bundle

```sh
# Pin the current chain head under the operator key (idempotent at an unchanged head).
npm run cli -- attest

# Export the attested event slice, the attestation, its signature, and the signer's
# public key. The database is opened read-only; export never mutates it.
tsx scripts/export-chain-evidence.ts bundle.json
```

Options: `--db <path>` selects a database (default: the local `.openmao` database),
`--workspace <id>` selects a workspace (required only when more than one has attestations),
and omitting the output path writes the bundle to stdout.

The bundle's event slice covers exactly the attested range — genesis through the attested
head. The attestation's own audit event advances the live chain past the attested head, so
events recorded after attesting are not covered; re-attest and re-export to cover them.

## Verifying a bundle

```sh
tsx scripts/verify-chain-evidence.ts bundle.json
```

Exit 0 with a JSON report on success; exit 1 naming the failed check otherwise. The verifier
reads only the bundle — no database, no network. The checks it performs are specified below
independently of that implementation, so a verifier can be re-implemented from this document
alone.

## What verification proves — and what it does not

A bundle that verifies proves:

1. **Integrity of the attested range as exported.** Every event hash recomputes from its
   contents, every link points at its predecessor, and the chain reaches the exact head the
   attestation pins. Truncating, rewriting, reordering, or inserting events breaks a check.
2. **Attestation authenticity.** The attestation's signature verifies, over the exact signed
   bytes, under an Ed25519 key, with the signed body bound to the attested head, the
   workspace, and the signer.

It does not prove, on its own:

- **Authorship.** The public key travels inside the bundle, so key substitution is detectable
  only against a key obtained elsewhere. Before treating authorship as established, confirm
  the bundle's `signer.public_key` against the operator key's fingerprint obtained out of band
  (the root-of-trust ceremony prints it at bootstrap and records it outside the database).
  Without that comparison you have verified self-consistency, not who signed.
- **Freshness.** The slice ends at the attested head. Anything the database did after
  attestation is outside the evidence; attestation cadence is the operator's control.
- **Individual non-repudiation.** Signing is server-side: the signature attests that the
  substrate, holding the principal's key, signed on presentation of the principal's
  credential. See [LIMITATIONS.md](LIMITATIONS.md) §2.

## Bundle format

```jsonc
{
  "format": "openmao-chain-evidence/v1",
  "exported_at": "<wall-clock export moment; metadata, not signed or hashed>",
  "workspace_id": "...",
  "genesis_hash": "000…000",        // 64 zero hex digits; every workspace chain starts here
  "events": [ /* canonical Event objects, seq order, genesis..attested head */ ],
  "attestation": {                  // the chain_head_attestations row
    "id", "workspace_id", "head_sequence", "head_hash", "event_count",
    "previous_attestation_id", "signer_key_id", "signer_principal_id",
    "signature_id", "attested_at"
  },
  "signature": {                    // the governance_signatures row it references
    "id", "object_type", "object_id", "signer_key_id", "signer_principal_id",
    "signed_bytes",                  // the exact JWS signing input: header.payload
    "signature",                     // base64url Ed25519 signature segment
    "domain_tag", "signed_at"
  },
  "signer": {
    "principal_id", "key_id", "algorithm": "Ed25519",
    "public_key",                    // raw 32-byte key, canonical base64url (RFC 8037 OKP x)
    "trust"                          // "standard" | "development_bootstrap"
  }
}
```

## The verification algorithm, implementation-independent

Three checks, each fail-closed, in this order.

### 1. Chain

For each event, in `seq` order:

- `prev_hash` must equal the previous event's `hash` — the first event's `prev_hash` must
  equal the genesis value (64 zero hex digits).
- `hash` must equal `SHA-256(canonical_json(event without its hash field))`, hex-encoded.

**Canonical JSON** is the repo's `dumpJson`, specified here as a protocol rather than a
helper: UTF-8 JSON with no insignificant whitespace, produced by recursively serializing plain
objects with keys sorted by JavaScript `String.prototype.localeCompare` and arrays in order.
Values that JSON cannot represent faithfully are rejected at production time rather than
normalized: `undefined`, functions, symbols, bigints, non-finite numbers, sparse arrays,
non-plain objects, and symbol-keyed properties never appear in a bundle. Note this is **not**
RFC 8785 (JCS): `localeCompare` ordering is locale-dependent in principle, deterministic in
practice for the ASCII field names these contracts use, and identical across conforming
Node.js runtimes. An independent verifier on another stack must replicate the observed key
order of the sample; when in doubt, sort code units ascending, which matches `localeCompare`
for pure-ASCII keys.

### 2. Anchor

The slice's last event must have `seq` equal to `attestation.head_sequence` and `hash` equal
to `attestation.head_hash`, and the slice length must equal `attestation.event_count`. This
is the truncation arm: deleting the newest events leaves a self-consistent chain whose head
no longer matches the value the attestation pins.

### 3. Signature

Split `signature.signed_bytes` at the single `.` into header and payload segments. Both
segments and `signature.signature` must be canonical base64url (URL alphabet, no padding,
decoding and re-encoding reproduces the segment exactly). Then:

- Decode the header: `alg` must be `"EdDSA"`, `typ` must be
  `application/vnd.openmao.chain-attestation.v1+json`, and `kid` must equal
  `signer.key_id` and `attestation.signer_key_id`.
- Decode the payload: `workspace_id`, `object_id`, `signer`, `signer_key_id`,
  `head_sequence`, `head_hash`, `event_count`, and `attested_at` must equal the corresponding
  bundle and attestation values. The signature row and attestation row must also agree on
  `signer_key_id`, `signer_principal_id`, and `signature_id`.
- Verify `signature.signature` as an Ed25519 signature over the exact ASCII bytes of
  `signed_bytes` (the RFC 7515 detached-JWS signing input) against the public key constructed
  as an RFC 8037 OKP JWK: `{"kty":"OKP","crv":"Ed25519","x":<signer.public_key>}`.

Any JOSE-capable verifier can perform check 3 unaided — the signed bytes are standard
RFC 7515, which is exactly why that format was chosen.
